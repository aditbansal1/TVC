Ranger is USC Liquid Propulsion Lab's vertical-takeoff, vertical-landing (VTVL) liquid-rocket vehicle. To steer, the engine sits on a two-axis gimbal pushed by two electric linear actuators (pitch and yaw). I own the thrust vector control (TVC) system from the flight computer to the actuator: the CAN-FD bus to the motor controllers, the real-time 50 Hz control thread, the gimbal kinematics, and the safety supervisor that decides when the actuators are allowed to move.

02Electrical interface: the CAN-FD bus

Why CAN-FD. Each actuator needs a 43-byte command-and-query frame every cycle. Classic CAN carries 8 data bytes per frame, so one command would need six frames. CAN-FD carries up to 64 bytes and can switch the data phase to a higher bit rate. Because CAN is a differential bus, it also tolerates the electrical noise around a firing engine far better than the single-ended PWM servo links used on our earlier test vehicle.

Physical-layer design decisions

DecisionReason
Transceiver with 3.3 V logic I/OTeensy 4.x pins are not 5 V tolerant; a 5 V-logic transceiver would damage the MCU
120 Ω at both bus endsmoteus boards have no on-board termination. The bus impedance is ~120 Ω, so an unterminated end reflects edges and corrupts bits
Twisted CAN_H/CAN_L + shared GNDNoise couples equally into both wires and cancels in the differential receiver; GND keeps both nodes inside the common-mode range
Standby pin tied for normal modeA floating standby/silent pin leaves the transceiver unable to drive the bus or ACK
1 Mbps arbitration / 5 Mbps data, BRS off at firstBench-validated at 1 Mbps first; switch to 5 Mbps data only after checking signal quality on the real vehicle harness

Bus timing budget (one 20 ms cycle)

Frame-time estimate

t_frame ≈ 67 bit / R_arb + (48 B·8 + CRC + stuffing ≈ 430 bit) / R_data ≈ 0.5 ms at 1 Mbps

That gives four frames, about 2 ms, inside a 5 ms reply window, which leaves margin for a retransmission and for bus load to grow when more nodes are added. A 48-byte frame was also a deliberate choice: I encode every position register as float32 rather than moteus' scaled int16 format, because int16 saturates at ±3.28 revolutions and the actuator travels about ±8 rev over ±12°. Spending 5 extra bytes per frame removes an overflow failure mode entirely.

Firmware ↔ hardware interface

  • Devicetree overlay enables FlexCAN3 on Teensy pins 31 (CTX3) and 30 (CRX3), sets both bit rates, and selects it as the board's zephyr,canbus. The build fails at compile time if CAN-FD is not configured.
  • Hardware acceptance filters on all 29 bits of the extended ID, one per controller. Each reply lands in its own message queue, and the CPU never sees unrelated traffic.
  • Non-blocking transmit: frames go into a hardware mailbox with a completion callback, so a missing ACK or a stuck bus cannot stall the control thread.
  • Watchdog on the motor controller: if commands stop for 100 ms (cable cut, MCU hang), moteus stops driving on its own. The hardware fails safe independently of my code.

Bringing up and debugging the physical layer

Approach: verify the bus one layer at a time, so a "no reply" symptom can be pinned to wiring, signaling, or firmware instead of guessing.

Method: probed CAN_H and CAN_L with an oscilloscope and checked the differential levels (recessive ≈ 0 V, dominant ≈ 2 V). Looked for ringing on edges, which points to termination problems. Measured ~60 Ω across H–L with power off, which confirms both 120 Ω terminators are present. Used SocketCAN (candump) to confirm frame IDs and ACKs independently of the MCU.

Firmware side: matched the 29-bit ID layout (prefix, source, destination, reply bit) and bit rates to the moteus configuration, and brought up one actuator at a time with a single-axis bench build, so each fault had only one suspect.

03Control chain: from gimbal angle to motor revolutions

Inverse kinematics (closed form)

L(δ)² = L_ts² + L_re² − 2·L_ts·L_re·cos(θ₀ + δ)

δ is the commanded gimbal angle and θ₀ is the angle between the fixed arms at center. Only L changes, so I precompute the constants at compile time. The inverse, δ(L) = acos(…) − θ₀, turns measured motor position back into an angle. Across ±12°, |dL/dδ| ≤ 0.115 in/deg, which I use to convert angular rate limits into actuator velocity limits conservatively.

Validated against the mechanical model: 241 test vectors per axis (−12° to +12° in 0.1° steps) from the team's MATLAB model, enforced by unit tests. While building them I noticed the supplied yaw table was identical to the pitch table, even though the MATLAB model gives yaw a different center angle (a ~0.35 in difference in center length). I flagged it to the mechanical team instead of guessing, and the yaw axis stays disabled until its geometry and motor direction are confirmed.

04Real-time design, verification, and results

Deterministic timing

  • Absolute-period scheduling: the loop waits on a periodic kernel timer instead of sleeping after its work. Sleeping after the work makes the period 20 ms plus execution time, so the loop drifts. Missed periods are counted as overruns rather than silently stretching the cycle.
  • Priority placement: the TVC thread sits below the main controller tick and above all sensor threads, so a slow sensor read can never delay an actuator command.
  • No priority inversion: the controller and TVC thread share one small struct behind a mutex. Both only copy data while holding it and never block or log inside it, so the controller never waits on the CAN bus.
  • Self-measuring: every cycle records period jitter, per-axis reply latency, cycle time and overruns, and streams them to the ground station.

Problems I found and solved

SituationReviewing the TVC code before bench testing, I found a path where every command could be pinned to a single actuator length. TaskRemove the hazard, even though unit tests passed, because it depended on link order. ActionThe cause was C++ static-initialization order. A geometry constant was computed at runtime, but the supervisor used it in its own global constructor, so on some link orders it read 0 and the length clamp collapsed. I made the constant constexpr (compile-time square root) with a static_assert on its value. ResultAn entire class of build-order bugs is now impossible, and a geometry change that breaks it fails at compile time instead of on hardware.
SituationControl logic runs on one 1.5 ms work queue; waiting there for CAN replies (up to 5 ms) would stall it, and the two raced on shared state. TaskMake the 50 Hz TVC loop deterministic without slowing the 1.5 ms controller. ActionMoved CAN onto a dedicated thread that alone owns the bus, paced by an absolute kernel timer, with a mutex-guarded hand-off. Moved logging out of the critical section (it could stall the controller) and fixed an undefined NaN-to-int conversion in the bench log. ResultThe controller tick never waits on CAN, and command-to-reply latency stays under 5 ms at a stable 50 Hz, with jitter and overruns measured every cycle instead of hidden.

What I learned

  • The electrical layer comes first. A missing terminator or a floating pin looks like a "software bug" until you put a scope on it.
  • Fail safe by design, in layers: firmware interlocks, a controller-side watchdog, and a mechanical home reference each cover the others' failures.
  • Refuse to guess. When data disagreed, I made the system refuse to run and escalated the question, instead of picking a number.
